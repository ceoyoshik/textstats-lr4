# Сравнительный анализ методов тестирования (ЛР №4)

## 1. Методы «чёрного ящика»

| Метод | Суть | Преимущества | Недостатки | Применение |
| --- | --- | --- | --- | --- |
| Эквивалентное разбиение | входы делятся на классы с одинаковым поведением | быстрый базовый набор | пропускает стыки классов | текст: пустой, пробельный, обычный, слишком длинный |
| Граничные значения | значения на границах классов | ловит ошибки сравнений | нужны точные границы | длина текста: 1, `MAX_TEXT`, `MAX_TEXT + 1` |
| Причинно-следственные связи | таблица «причина → следствие» | системность | таблица быстро растёт | проверки версии и полей ответа |
| Предположение об ошибке | предугадывание типичных ошибок | дёшево, находит реальные дефекты | зависит от опыта | точка без пробела, `\x00`, эмодзи, дефисы, апострофы, числа |

## 2. Методы «белого ящика»

| Критерий | Что гарантирует | Стоимость | Итог |
| --- | --- | --- | --- |
| Покрытие операторов | каждая строка выполнена | низкая | 100 % |
| Покрытие решений | обе ветки каждого `if` | средняя | 100 % (требование варианта 11) |
| Покрытие условий | каждое простое условие истинно и ложно | высокая | `is_number`, `parse_response` |
| Комбинаторное покрытие | все комбинации условий | очень высокая | `check_version`: 5 достижимых из 8 |

## 3. Почему для варианта 11 выбран метод «покрытие решений»

1. Программа состоит из коротких функций с явными ветками (пустой текст,
   нет слов, лимит частот, ошибки протокола) — покрытие решений напрямую
   проверяет каждую из них.
2. Метод даёт объективный критерий готовности: все ветки пройдены, значит
   ни одна ошибочная ситуация не осталась без обработки.
3. Комбинаторное покрытие для `parse_response` дало бы более сотни
   комбинаций при небольшой дополнительной пользе, поэтому применено
   выборочно.

## 4. Сравнение «чёрного» и «белого» ящика

| Критерий | Чёрный ящик | Белый ящик |
| --- | --- | --- |
| Источник тестов | ТЗ и варианты ввода | исходный код |
| Что находит | несоответствие требованиям, границы | непроверенные ветки, необработанные ошибки |
| В работе | все 3 дефекта найдены тестами по границам | 100 % покрытие подтвердило полноту ветвей |

Практический вывод: 100 % покрытие без анализа границ не нашло бы
BUG-1…BUG-3 — они возникают на конкретных «неудобных» данных.

## 5. Инструменты

| Инструмент | Плюсы | Минусы | Выбор |
| --- | --- | --- | --- |
| pytest | короткий синтаксис, параметризация, маркеры | требует установки | выбран |
| unittest | входит в stdlib | многословный | не используется |
| coverage.py | отчёты по строкам и ветвям, порог сборки | не оценивает качество проверок | в CI |
| flake8 | быстрый, единый стиль | не находит логических ошибок | в CI |

## 6. CI/CD-платформы

| Платформа | Особенности |
| --- | --- |
| GitHub Actions | YAML в репозитории, матрица версий, артефакты — используется |
| GitFlic | российская платформа, встроенный CI |
| GitFlame | российский хостинг с CI |
| Mos.Hub | платформа для госсектора, CI на базе GitLab |

Пайплайн переносится на российские платформы без изменений: те же шаги
(зависимости, flake8, pytest, coverage).
